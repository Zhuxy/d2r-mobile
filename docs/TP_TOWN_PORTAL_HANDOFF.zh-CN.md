## 2. 用户确认的最终交互

1. 使用现有固定位置的回城按钮，不占普通技能快捷栏。
2. 人物具备 TP（装备非职业技能、正手或副手聚气等）时，大图标变 TP；原回城图标缩小叠在右下角。
3. **快速按下并抬起：TP 一次**。若 TP 来自副手，自动切过去、施放、再恢复原武器组。
4. **原地按住超过半秒，再向按钮外拖动并释放：回城**，开蓝门后自动进入蓝门。
5. 此特殊按钮不采用“按住持续施法”的逻辑；只有上述两种释放手势。单纯长按不放技能，过早滑出取消。
6. 没有 TP 来源时，仍是普通回城按钮。

用户没有确认“固定朝镜头前方传送 23 格”这一目标算法。这是第二版临时实现，**不要当成产品需求**。

## 4. 现有调用链

```text
UIKit touch
  -> dm_touch_controls：手势识别
     -> portal_tp_seq 改变
        -> front_ios.m -> dm_quicktp_request()
           -> 原子请求位
           -> hle_hid.c 取手柄处先调用 dm_actions_pump()
           -> swapskill_pump() -> Q_* 事务
     -> portal_town_seq 改变
        -> front_ios.m -> dm_world_portal_home_request()
           -> dm_world_pump() -> w_auto_portal_step()
           -> dm_tp_request() -> dm_freetp_server_step()
           -> 找到新蓝门 -> w_go() -> 原有移动/交互

服务端每拍 diag.c
  -> dm_swapskill_srv_wset()：发布武器组
  -> dm_quicktp_srv_selection()：发布右手技能号与来源物品
```

`front_ios.m` 的 portal 手柄 mask 保持为 0；新触屏按钮靠宿主请求触发。没有 TP 时，普通回城目前在 **touchesBegan** 触发；有 TP 时，二合一手势在 **touchesEnded** 判定。这个时机差异是当前代码事实，不是另行确认的需求。

手势字段：每根手指有 `portal_tp / portal_armed / portal_moved_early`；全局有 `portal_tp_enabled / portal_tp_seq / portal_town_seq`。移动、tick 和释放时都会按事件时间判断是否已按够半秒，避免掉帧导致长按失效。UIKit 坐标单位为点，阈值随布局比例缩放。

来源判断目前在 `quicktp_source()`：

- 优先当前技能链中来源物品为 `-1` 且等级大于 0 的 54 节点，作为自学/非物品来源。
- 再扫当前物品链的已装备项，检查 stat 97 或 stat 204；副手位允许暂时没有客户端技能节点。
- 优先当前组，其次 oskill；忽略聚气为 0 的纯 charged 来源。
- `dm_quicktp_state()` flags：1=存在来源，2=需要换另一武器组，4=聚气；这些只说明“来源存在”，**没有完整检查法力、城镇、动作、死亡、落点等实际可施放条件**。
- 装备 oskill 最终可能以来源 `-1` 合并进技能链；需要用真实装备分别验证，不要假定所有来源都以装备 id 存在。

## 7. 第二版（用户报告的两个问题）与第三版（当前工作区）

第二版把传送做成独立 `Q_*` 状态机，不再修改 ZR 表、不注入 TP 按键（状态机的骨架第三版沿用）：

| 状态 | 当前动作 |
| --- | --- |
| `Q_IDLE` | 接收请求；要求普通 `SS_*` 空闲、存在来源、武器组可读、非死亡/城镇/面板、客户端不在动作中；不满足就丢弃该请求 |
| `Q_SWAPPING` | 若来源在另一组，调用原版换武器；等服务端组变化和客户端对应来源节点出现；带有限次数重试与超时 |
| `Q_SELECT` | 保存当前客户端右手技能号/来源；调原版选技能入口 `main+0x43f170(54, 0, 物品 id)`（它自己发 9 字节 `0x3c`，并把 `[玩家+0x100]+0x10` 指到该节点）；读取节点聚气数作为基线 |
| `Q_CAST` | 等 diag 发布的服务端右手技能号=54、来源=请求物品，再调原版右手点击入口 `main+0x4ace20(玩家, 9, x, y, 0)` 施放（动画与包都是原版的）；返回 0 或 25 拍未确认则取消施放并恢复 |
| `Q_WAIT` | 聚气来源以节点次数减少判断成功；其他来源以客户端整数坐标变化判断；45 拍超时也进入恢复 |
| `Q_RESTORE` | 等客户端动作结束（最多等待 70 拍），用 `main+0x43f170` 选回之前的右手技能，然后进入切回 |
| `Q_BACK` | 如果服务端组已恢复或死亡就结束；否则隔一段时间重试原版换武器，尚无总超时 |

### 第三版：施放与落点改成调原版入口（当前工作区实现，未实机验证）

用户对第二版的两条反馈是「TP 的动画没有了」「没有对着人物面向的方向飞」。两条都指向同一个根因：**第二版自己拼 `0x3c` / `0x0c` 包，只改了服务端，客户端根本没有选中这个技能、也没有起施放动作**——所以没有动画，落点只能由宿主自己按镜头 / 上一次左摇杆方向瞎算。第三版把这两步都交回原版：

| 步骤 | 调的原版入口 | 证据 |
| --- | --- | --- |
| 选右手技能 | `main+0x43f170(技能号, 0 = 右手 / 1 = 左手, 物品 id)` | 客户端技能链表里按「技能号 + 物品 id」找节点 → 自己发 9 字节 `0x3c`（`0x80000000` 位 = 左手）→ 右手走 `0x5aee00`（只写 `[玩家+0x100]+0x10`，不碰服务端） |
| 施放 | `main+0x4ace20(玩家, 9 = 右手按下, 格 x, 格 y, 0)` | 动作 7 / 9 = 原版左手 / 右手按下（`0x2b5c38` 是手柄主键的 7，读 `+0x8`；9 读 `+0x10`）；内部 `0x4b83b0` 按动作号组 5 字节包——右手对地施放 = 动作 12 → 包 `0x0c`（`0x4b8b44`：`strb w23(动作号)` + 两个 `sturh` 坐标 + `send(…, 5)`，即第二版自己拼的那一包逐字节相同），并先起客户端动作（动画） |
| 位置与朝向 | `main+0x2b4ef8(管理器, 玩家, &pos, &dir)` | 无指定目标时 `dir` 就是人物面向（与本仓 `hle_private_aim.c` 里「按住重放回退到角色朝向」的实测一致），返回前已归一化 |
| 落点距离 | `main+0x2b4bc8(管理器, 54)` 的记录 `+8` = defaultTargetDistance（传送 23），取不到用 23 | 与本仓 `hle_private_aim.c` 同一读法 |

落点 = `截断(pos + dir × 距离)`（`fcvtzs`，与原版 `0x2b5c34` 一致）。这就直接回答了用户第 2 条：**现在朝人物面向飞 23 格**；镜头 / 摇杆不再参与。`0x4ace20` 会优先用管理器 `+0xd10` 的「指定目标」，调用前后临时清空 / 还原（同 `dm_world.c` 的交互调用），防止拖技能钮选怪的残留目标把传送拐走。

仍然**没有实机证据**，可能出错的地方：

- 动作号 9 是否就是原版右键放技能那条路：结论来自 `0x4ace20` 的跳转表（9 → `0x4ad3f4` 读 `+0x10`）和标志位分派（`0x4ae3b0` 里 bit1 → 动作 12 → 包 `0x0c`），**没有真机对照**。若服务端确认了技能却看不到施放动作，等价的另一条是左手：`0x43f170(54, 1, 物品 id)` + `0x4ace20(…, 7, …)`，并把 `diag.c` 发布的槽从 `+0x10` 换成 `+0x8`。
- 原版点击入口自身的前置条件（能否施放、动作中、指定目标）由它判，返回 0 时日志会打「【红】没起施放」；返回非 0 也只说明它收下了这次点击，不等于服务端接受了传送。
- 客户端 `+0x10` 被换成传送后是否会残留（`Q_RESTORE` 的选回同样走原版入口，节点不在时返回 0 并打红线）。
- 第二版那套服务端发布 / 确认逻辑原样保留，所以 `diag.c` 的成对快照问题、`Q_BACK` 无总超时、请求在动作中被吃掉等风险**都还在**。

第二版附带行为：

- `diag.c` 通过两次独立 atomic store 发布服务端技能号和物品 id，没有采样序号/玩家或场景身份，读取也不是成对快照。
- `dm_swapskill_busy()` 把 `Q_*` 算入 busy，阻止自动增益开启新一轮换武器，但是否能阻止已在执行的自动增益事务冲突还没验证。
- TP 事务大部分阶段会屏蔽 A/B/X/Y/R/ZR，`Q_BACK` 阶段放行普通按键，避免切回一直失败时完全锁住技能操作。
- 通用 `SS_BACK` 从“最多三次后放弃”改成持续重试；这是**影响原有快捷技能和技能树恢复**的共享行为变更，需要关注回归。


### 第二版遗留的落点算法已被换掉

第二版自己记录请求时坐标、按最近非零左摇杆 / 镜头朝向算方向、硬编码 23 格；**第三版已删掉这段**，改用原版 `0x2b4ef8` 的朝向 + `0x2b4bc8` 的距离（见上表）。如果仍要复核方向：`dir` 来自人物路径结构（`+0x38` 的 `+0x20` / `+0x80` 角度字节转弧度），管理器 `+0xd2c/+0xd30` 非零时（游戏里有指定点地目标）会改朝那个目标——触屏走路用摇杆、点地移动包又被丢弃，正常不会有残留，但实机若发现「方向朝着刚才点过的怪物」，先查这两处。

当前代码记录请求时坐标 `(qx0,qy0)`（只用于 `Q_WAIT` 判断「有没有位移」），不再拿它算目标；方向也不再取镜头或左摇杆。第二版那段「左轴 / `dm_cam_heading()` / 硬编码 `(1,0)` × 23 格」已经删除，`dm_quicktp_last_stick()`（`hle_hid.c`）一并删掉。

## 8. 回城并自动进门：有一段成功的实机证据

## 9. 建议接手排查顺序

1. **先确认运行版本和最新失败现场**：用户最新的“仍有问题”没有第二版具体症状。确认 App 是否包含 `原版传送包` / `服务端未确认右手传送技能` 等第二版日志，避免拿旧包测试新源码。前一 agent 没有为第二版做完整 App build 或安装，只做了语法检查。
2. 用用户相同角色和 TP 棒，先在原有普通技能栏绑定 TP，录一次本来能工作的“切副手—TP—切回”作为基准。用户此前描述此普通快捷栏功能已存在且能工作；本 agent 没有重新实测这一基准。
3. 录二合一同一操作，比较实际 `0x50 / 0x3c / 0x0c`（以及可能的其他施放包）顺序、长度、源物品 id、左右手标志、目标坐标及服务端处理结果。仓库有 `DM_C2S_LOG`、`DM_TEST_POS_LOG`、`DM_TEST_BINDTBL=log`；见 `diag.c`、`dm/verify/command_packet_format.zh-CN.md`。不要只看 HUD 动作。
4. 每步同时记录客户端和服务端：玩家 id/区域/武器组、模式、左右手节点技能号+来源、聚气数、坐标；至少能区分“没发请求、没切过去、技能没选中、没发施法包、服务端拒绝/落点问题、已施法但没切回”。
5. 原版正常 TP 的入口已经弄清（选技能 `0x43f170` + 右手点击 `0x4ace20` 动作 9 + 朝向/射程 `0x2b4ef8` / `0x2b4bc8`），剩下要确认的是**动作号 9 是否真等于原版右键放技能、以及原版点击入口在实机上的返回值和后续动作**；对照手段仍是录下原版 `0x3c / 0x0c` 与宿主这两次调用的结果。
6. 对照原版明确解释切回失败。持续重试只能减少放弃，**不是原因修复**；可能仍有客户端状态、服务端动作/组号、装备引用、正在执行的其他事务或包内容的问题。

当前实现还应检查的具体风险（均为代码审查线索，尚未实测证明是本次根因）：

- `Q_CAST` 只匹配服务端技能/物品 atomic，未证明快照属于当前请求；跨局/换人时存在旧值窗口。
- 直接发包可能缺少客户端原生选技能/预测/控制器状态更新；现有动画与费用处理是否能仅凭这些包正确完成仍未知。
- 无聚气来源以坐标变化算成功，玩家普通走动也能误判；聚气来源只看客户端节点 `+0x48`，还应核服务端物品 stat 204 和位移，不能只看到扣次就判目标效果成功。
- `Q_BACK` 无总超时，会持续占用 busy、阻止自动增益和新的二合一 TP；虽放行技能键，仍可能与用户操作互相干扰。
- `atomic_exchange(g_qtp_req,0)` 在动作中/已有事务时直接吃掉请求，用户可能表现为点了无反应。
- TP 未结束时又长按回城、自动增益已在执行、技能树页签换组等事务，目前没有统一仲裁。
- 原有 `SS_READY` 仍保留“动画 busy 也算看见施法”的判据。第二版 TP 已不复用它，但普通副手快捷技能仍受它影响。
- 当前 UI “有 TP”并不等于 TP 此刻可施放；还要确认无聚气、装备变化、原生职业 TP、谜团、正/副手多来源等情形。

### 其他研究过但尚未采用的路径

- `dm_freetp.c` 和 `dm_autobuff.c` 会在服务端拍临时替换技能链右手节点，调用 `main+0x6e77f0(G,player,x,y,1,node)`，调用后恢复节点。现有回城/增益用过，**没有证明用于 charged Teleport 会正确扣聚气并保持客户端同步**，不要直接复制后宣称完成。
- `dm_teleport` 是底层直接迁移单位坐标的工具，不能拿它替代正常 TP 来掩盖技能施放和费用失败。

## 10. 原映像换武器反汇编记录

本机有 `dm/host/tests/build/main.orig.bin`（约 50 MiB，未修改）。已读取 `0x41db90` 起的 ARM64 原指令，观察到该客户端函数最终构造长度 **0x1e = 30** 的 `0x50` 包：

| 包偏移 | 函数中可见的写入 |
| --- | --- |
| `0x00` | `0x50` |
| `0x01 / 0x05 / 0x09 / 0x0d` | 四个装备单位 id（具体栏位顺序未在本次追完） |
| `0x11 / 0x15` | 左/右技能节点 `+0x44` 的来源物品 id |
| `0x19 / 0x1b` | 左/右技能记录首 u16 技能号 |
| `0x1d` | 调用参数 `currentSet & 1` |

这说明换武器包**不只是一个切换键或组号**，还携带装备和技能信息；第二版直接改右手选择是否影响切回包也值得对照。以上是函数组包观察，不等于已验证服务端接受条件。

本机没有 Python capstone，也没有 `llvm-mc`；`xcrun llvm-objdump` 可用。原始 `.bin` 不能直接正常反汇编时，前一 agent 用 Python 把所需区间每 4 字节写成 ARM64 汇编 `.long`，`xcrun clang -target arm64-apple-macos -c` 生成临时 Mach-O，再 `llvm-objdump -d`。注意这样打印的地址从临时片段 0 起，分支目标要加回原区间基址，不能直接当 main 偏移。临时文件曾在 `/tmp/swap*.s`、`/tmp/swap*.o`。

## 12. 给下一个 agent 的首条任务

第三版把施放与落点交给原版入口后，最需要先确认的是**动作号对不对**：实机点一次 TP，看三件事——(a) 日志是否出现 `原版右手施放入口（返回 非 0）`，(b) 有没有原版的传送动作动画，(c) 位移方向是否等于点按钮那一刻人物面向、距离约 23 格。

- 若返回非 0 但没有动画、也没有扣聚气：说明动作 9 起的是别的动作，按第 7 节末尾那条改成左手（`0x43f170(54, 1, …)` + `0x4ace20(…, 7, …)`，同时把 `diag.c` 发布的槽从 `+0x10` 换成 `+0x8`）。
- 若返回 0：看同拍日志里管理器 `+0xd10`（指定目标）、客户端是否在动作中、`ss_node` 是否真的找到了节点。
- 若动画和位移都对，只差扣费/切回：那是第二版原有的 `Q_WAIT` / `Q_BACK` 问题，按第 9 节继续。

不要在没拿到实机日志前再加新的启发式（尤其是再自己算方向），也不要直接迁移人物坐标来绕开技能施放。
